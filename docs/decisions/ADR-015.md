# ADR-015: 图标尺寸与描边的单位口径

## Status: Accepted (2026-09-19)

## Background

出现一次「规格冲突」上报：
- 架构侧锁定「24 网格 / 2px 描边」
- `docs/design/DESIGN.md` §5.1 写「描边 = size / 12」（即 16→1.33、20→1.67、24→2）

设计侧据此认为两者不一致，前端无法定 `strokeWidth`，提议按尺寸光学缩放（24→2 / 20→1.75 / 16→1.5）。

**复核结论：这是假冲突。** 两者是同一结论的两种单位口径，数值完全相等。

## Decision

### 1. 两者等价（不存在冲突）

Tabler 的 `stroke` 是 **24 viewBox 下的用户单位**，渲染 CSS 像素为：

```
rendered_px = stroke × size / 24
```

取 `stroke = 2`：

| size | 渲染像素 | 等于 |
|---|---|---|
| 24px | 2 × 24/24 = 2.00 | 24/12 |
| 20px | 2 × 20/24 = 1.67 | 20/12 |
| 16px | 2 × 16/24 = 1.33 | 16/12 |

即 `size / 12`。**§5.1 写的是渲染像素口径，架构侧写的是 SVG 用户单位口径。** §5.1 内容无需修改。

### 2. §5.1 必须补单位声明（真事故风险）

现有写法存在实际风险：前端可能理解为"把 `size/12` 当作 `stroke` 传入组件"。那会**二次缩放**：

```
16px 传 stroke={1.33} → 实际渲染 1.33 × 16/24 = 0.89px  // 几乎不可见
```

§5.1 必须改为：

> 描边（**渲染 CSS 像素**）= size / 12。实现上恒定传 `stroke={2}`（24 网格用户单位），由组件自动缩放得到上述值；**禁止按尺寸计算 stroke 值传入**。

### 3. 驳回按尺寸光学缩放

采用单一常量，**三档共用**：

```ts
export const ICON_STROKE = 2;   // 24 网格用户单位，16/20/24 三档共用
```

驳回理由：
1. **Tabler 字形是按 2/24 比例整体调过光学的** —— 笔画粗细与内部留白（counter）、端点间隙是配套设计的。16px 下把比例抬到 1.5，等于改动设计者调好的笔画-留白关系，同一套图标在三个尺寸下会出现三种性格
2. **「糊」只在 1x 屏成立** —— 2x 屏下 1.33 CSS px = 2.67 设备像素，是清晰的。本产品是本地开发者工具，目标机器以 2x 为主
3. **单一常量零漂移** —— 无按尺寸分支，无散落魔数

**反转路径**：该常量就一行。若能提供 **1x 屏 16px 的实拍截图**证明确实糊，立即改为光学缩放表，无需再行说服。空口论证不够，截图够。

### 4. 尺寸由 `AppIcon` 收口

类型层只接受 `16 | 20 | 24`，其他值编译不过。单一收口点，避免全项目散落 size。

## Consequences

**正面**
- 消除"二次缩放导致图标几乎不可见"的潜在事故
- 单一常量，A/B 与后续调整都只改一处
- 视觉一致性由单一 stroke 比例保证

**负面**
- 若目标用户存在大量 1x 屏，16px 图标观感偏弱（已留反转路径）

## 流程改进（架构侧责任）

本次误判源于**双方未提前统一单位口径**。架构侧曾按"1.75 = 用户单位"计算并判定设计侧"方向反了"，若 1.75 实指渲染像素则**该判定错误**。

**此后所有尺寸 / 描边 / 间距规格一律显式标注口径**（渲染 CSS 像素 或 SVG 用户单位）。此项为架构侧流程约束，不归责设计侧。
