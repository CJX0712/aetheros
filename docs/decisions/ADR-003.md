# ADR-003: 存储与检索选型

## Status: Accepted (2026-09-19)

## Background

本地优先意味着零外部服务：不能有数据库守护进程。同时需要三件事：结构化审计数据（runs/spans/evidence）、全文检索（BM25）、向量检索（dense）。

SPEC §3 明确"禁止自研向量数据库——SQLite FTS5 已足够"，并给出迁移触发条件："单机语料超百万 chunk 且 FTS5 无法满足召回时延目标时"。

候选：
- **SQLite 3.53.4（2026-07-24，sqlite.org）+ better-sqlite3 13.0.3（2026-08-05，snyk）**
- Node 内建 `node:sqlite`（22.x 起实验性）
- PGlite / libsql

## Decision

**选定 SQLite + better-sqlite3 13.0.3。**

- FTS5 齐备（含 trigram 分词器，中文必需，见 ADR-010）
- 同步 API 简单、事务语义清晰、零服务进程
- better-sqlite3 预编译二进制覆盖主流平台

**向量检索：MVP 阶段用 `BLOB` 存 `Float32Array` + 暴力余弦。**

- 适用规模 ≤ 50k chunk
- 超过则触发迁移评估（引入 sqlite-vec 或同等方案），届时需新立 ADR
- **迁移路径候选：sqlite-vec 0.1.9** —— 该版本已在 Windows 上验证可用（KNN 跑通，2000×512 索引 0.20s、top-10 查询 1.97ms）
- ⚠️ **但该次验证的宿主是 Python 的 `sqlite3` 模块，不是本产品的 better-sqlite3 13.0.3**。二者 SQLite 构建与编译选项不同（扩展加载能力 `SQLITE_ENABLE_LOAD_EXTENSION` 与架构位宽均需匹配）。**正式写入本 ADR 前必须在 better-sqlite3 下以 npm 取件（`sqlite-vec` + `sqlite-vec-windows-x64`）+ `db.loadExtension()` 重验**，不得以 Python 侧结果推定
- **本次不引入 sqlite-vec**：SPEC §3 明文"SQLite FTS5 已足够"，提前引入属范围变更，须走 SPEC §13 流程，不在架构层单方决定

出局理由：
- `node:sqlite`：22.x 仍为实验性，稳定性与自定义函数支持不及 better-sqlite3
- PGlite / libsql：引入额外运行时体积，且 FTS5 trigram 支持不确定

## Consequences

**正面**
- 单一文件数据库，备份 / 导出 / 审计包天然简单
- FTS5 的 `bm25()` 直接给出 BM25 分数，无需自研打分
- 暴力余弦在小规模语料上召回质量与专用索引等价，且零额外依赖

**负面**
- 暴力余弦复杂度 O(n)，50k chunk 以上时延上升
- 单写入者模型，需 WAL + 批量写（见下）

## 关联硬约束

- `PRAGMA journal_mode = WAL`
- **禁止逐 span 同步 insert** —— trace 写入必须批量（512 条 / 5s）
- FTS5 外部内容表模式（`content = 'chunks'`）配同步触发器，避免文本双份存储
- 审计表（spans / evidence / outbound_requests / hash_chain）由触发器强制 append-only（AC-10）
