# ADR-011: 证据区间编码（byte + utf16 双区间）

## Status: Accepted (2026-09-19)

## Background

glassbox 的核心承诺是"证据可溯源到字符区间"，UI 需要在原文中高亮命中的片段。设计侧最初提出只存 `byteStart / byteEnd`。

**只存字节区间不够。** JavaScript 的 String 索引是 **UTF-16 code unit**，不是字节。UI 拿到字节区间，在解码后的字符串上直接切片，遇到任何非 ASCII 字符就会静默错位——不报错、不崩溃、只是高亮错了位置。这正是最难查的那类失效：编译过、跑得动、结果错。

中文语料是本产品的主要场景，该问题必然触发。

## Decision

**同时存两套区间，各司其职：**

```
document_hash            源文件字节的 SHA-256，证据链的信任根
byte_start / byte_end    权威地址，可回源文件校验，抗重新编码
utf16_start / utf16_end  渲染用，对齐 JS String 索引，建索引时派生一次
```

- **`byte_*`** —— 权威地址。源文件被重新编码或换行符变化时仍可定位，且可与 `document_hash` 一起做完整性校验
- **`utf16_*`** —— 渲染用。UI 高亮直接 `text.slice(utf16Start, utf16End)`，零换算

### 不变式（必须测试）

```
decode(document_bytes)[utf16_start : utf16_end] === chunk_text
```

- 该断言在入库时执行，失败即入库失败，不静默通过
- **中文语料必跑**，至少包含：纯中文、中英混排、含 emoji（代理对）、含 CJK 扩展区字符

## Consequences

**正面**
- 消除中文证据锚点静默错位这一核心失效模式
- `byte_*` 提供可验证性（回源文件重算），与"可验证 RAG"的产品定位一致
- 渲染路径零换算，UI 侧实现简单

**负面**
- 多两个字段的存储与同步成本
- 入库时多一次不变式计算（可忽略）

## 关联硬约束

- 哈希不匹配的处理：**检索成功但内容哈希与入库时不一致 → 判 `failed`**，文案「内容哈希与入库时不一致，该来源已变更，证据链不可信」。**不得降级为 `unverified`** —— "已验证"是核心承诺，哈希对不上必须定性为不可信
- 五态互斥：`verified` / `unverified` / `refused` / `failed` / `error`（SPEC §8.1）

## 断言与证据关联的 null 语义

`claim.evidenceChunkIds` 区分两种情形，**不可合并**：
- `null` —— 系统未产出证据（未检索 / 生成失败）→ UI 渲染「无证据」告警态
- `[]` —— 检索执行但零命中 → UI 渲染「检索为空」态

合并会丢失"我明确找不到依据"这一最有价值的信号。Zod：`z.array(z.string()).nullable()`。
