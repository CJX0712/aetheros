# ADR-017: autoThreads 语义裁定（AC-02 夹取 vs AC-03 具名失败）

## Status: Accepted (2026-09-19)

## Background

F1「CPU 推理 sane defaults」有两条验收标准，措辞在实现时产生了歧义：

- **AC-02**（PRD，Event-driven）：`WHEN the runtime initializes local inference, the runtime shall set the inference thread count to autoThreads() and shall clamp the result to the inclusive range [2, 4].`
  → 说的是**自动推导路径**（无参调用）的结果必须夹到 `[2, 4]`。
- **AC-03**（PRD，Unwanted）：`IF any code change causes autoThreads(n) to return a value outside [2, 4] for any input n, THEN the test suite shall fail with a named assertion error.`
  → 说的是**防回退不变量**：对任意输入 `n`，`autoThreads(n)` 都不得**返回**越界值。

歧义点：当调用方**显式**传入越界值（如 `autoThreads(99)`）时，应当「夹到 4 并返回」还是「具名报错」？

`kernel.test.ts` 里同一 describe 块内的两条用例给出了**互相矛盾**的期望：

```ts
// 用例 A —— 期望夹取
const t = autoThreads(99);
expect(t).toBeGreaterThanOrEqual(MIN_THREADS);   // 实际：抛错，用例失败
// 用例 B —— 期望抛错
expect(() => autoThreads(1)).toThrow(/outside the clamp window/);
```

根因：该仓库首次提交时从未安装依赖、`pnpm verify` 从未真正执行过，两条用例都是未执行状态下写下的，矛盾因此未被发现。

## Decision

**AC-02 管自动推导（夹取），AC-03 管显式越界（具名失败）。二者不冲突。**

1. `autoThreads()` 无参调用 → 按核数推导后夹到 `[2, 4]`，**永不抛错**（AC-02）
2. `autoThreads(n)` 且 `n ∈ [2, 4]` → 原值返回
3. `autoThreads(n)` 且 `n ∉ [2, 4]` → **抛出具名错误** `autoThreads: requested N is outside the clamp window [2, 4]`（AC-03）

**取证**：AC-03 的措辞是「不得**返回**越界值」。越界输入抛错时函数根本没有返回值，不变量空真成立；而「显式要求越界」正是 AC-03 点名要拦的行为（`A caller that expects an out-of-window value to be honored gets a named failure instead`）。若改为静默夹取，调用方传入 99 会拿到 4 却毫不知情，反而掩盖配置错误。

用例修正（`kernel.test.ts`）：
- 用例 A 改为调用无参 `autoThreads()` —— 这才对应 AC-02 的自动推导语义，且保留「regardless of core count」的原意
- 新增用例：窗口内显式请求原值返回（补齐不变量的另一半）
- 用例 B 追加 `autoThreads(99)` —— 把 A 原本想覆盖的 99 并入越界断言

于是完整覆盖「永不越界返回」的两分支：窗口内原值返回 / 窗口外不返回。

## Consequences

**正面**
- 两条验收标准各归其位，不再互相打架
- 配置错误快速暴露（fail fast），而非被静默吞掉
- 不变量「对任意 n 都不返回越界值」有了穷尽性用例

**负面**
- `autoThreads(n)` 对越界 `n` 会抛错，调用方需要处理（当前仅 bench 与运行时调用，均走无参路径，无实际影响）
- 与「夹取一切」的直觉相反，需靠本 ADR 防止后人改回
