# ADR-010: 中文全文检索分词策略（FTS5 trigram）

## Status: Accepted (2026-09-19)

## Background

glassbox 的 BM25 检索必须支持中文语料。SQLite FTS5 的默认分词器是 `unicode61`，它按 Unicode 词边界切分——**对中文连续文本基本不切词**，整段中文会变成单个 token，BM25 检索形同虚设。

这是本地优先方案最容易静默失效的一处：不报错、能跑、结果永远不对。

候选：
- **FTS5 `tokenize = 'trigram'`**（SQLite ≥ 3.34.0 内建）
- FTS5 `unicode61`（默认）
- 外部分词器（jieba-wasm 等）预切词后存入

## Decision

**采用 FTS5 trigram 分词器，外部内容表模式。**

```sql
CREATE VIRTUAL TABLE chunks_fts USING fts5(
  text,
  content = 'chunks',
  content_rowid = 'id',
  tokenize = 'trigram'
);
```

- 目标 SQLite 3.53.4（2026-07-24），远高于 trigram 所需的 3.34.0 下限
- 零外部依赖，与"禁止自研向量数据库 / 禁止重造轮子"一致
- 外部内容表模式避免文本双份存储，配同步触发器

### 实测验证（2026-09-19，team-architect-2）

同库对比实测，trigram 与 unicode61 的中文行为差异被直接观测到：

| 分词器 | 查询词 | 命中 |
|---|---|---|
| `trigram` | `相似度` | **1 命中** |
| `trigram` | `BM25` | **1 命中** |
| `unicode61`（默认） | 同上中文查询 | **0 命中** |

该结论**与宿主无关** —— FTS5 分词属 SQLite 核心行为，不依赖宿主运行时，因此可直接应用于本产品的 better-sqlite3 13.0.3 + SQLite 3.53.4 组合。本 ADR 的决策由此从"依据文档推断"升级为"已实测确认"。

同时确认：**不需要引入中文分词器**（jieba 等）。trigram 已覆盖中文子串检索，省掉一个外部依赖与相应的构建复杂度。

## Consequences

**正面**
- 中文子串检索可用，且无需引入分词模型或 wasm
- `bm25()` 函数直接给出 BM25 分数，无需自研打分
- 无额外运行时依赖，离线可用

**负面（关键限制，必须处理）**
> **trigram 以 3 个字符为最小单位**：查询词长度 < 3（尤其是中文单字、双字词）**不会命中 FTS 索引**。

应用层强制要求：
1. 检索入口对查询词长度做分支：≥ 3 字符走 FTS5；< 3 字符降级为 `LIKE` 兜底
2. 若降级路径也不可用，必须**显式返回空并提示**，**不得静默返回 0 条** —— 静默空结果会被误判为"语料里没有"，是典型沉默逻辑错误
3. 该分支必须有测试覆盖（中文单字 / 双字 / 三字各一例）
